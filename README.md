# WP Panda Update Vault

Самостоятельное приватное хранилище релизов WordPress-плагинов и тем с совместимым клиентом автообновлений. Клиент использует штатный механизм WordPress: на странице **Консоль → Обновления** и в списке плагинов/тем появляются доступные обновления, а установку выполняет стандартный WordPress upgrader.

**Полная инструкция на русском:** [docs/USER_GUIDE_RU.md](docs/USER_GUIDE_RU.md) — установка, production-развёртывание, сборка ZIP, подключение к плагину/теме, выпуск релизов, безопасность и устранение неполадок.

> Это готовый MVP для самостоятельного развёртывания, а не SaaS. Перед публикацией в интернете обязательно задайте свои секреты, включите HTTPS и настройте резервное копирование `DATA_DIR`.

## Возможности

- Веб-панель на русском: каталог продуктов, релизы, размер архивов, счётчик скачиваний, загрузка ZIP и удаление продукта.
- Отдельные API-ключи для плагинов и тем. На сервере хранится только SHA-256-хеш ключа; исходный ключ показывается при создании/ротации один раз.
- Архивы хранятся в `DATA_DIR/packages`, вне публичной директории приложения, с правами `0600`. HTTP-маршрута для просмотра каталога нет.
- Клиент передаёт ключ в заголовке `Authorization: Bearer …` только при проверке обновления. Для скачивания сервер выдаёт подписанную HMAC-ссылку сроком на 10 минут. Ссылка не раскрывает путь к файлу и не содержит API-ключа.
- Заменить ключ или удалить продукт можно в панели. Ротация немедленно отзывает старый ключ.
- Приложение использует только стандартный Node.js — сторонние пакеты для запуска не нужны.

## Быстрый запуск

Требуется Node.js 18 или новее.

```bash
cp .env.example .env
# Отредактируйте .env: задайте уникальные ADMIN_PASSWORD, APP_SECRET и API_PUBLIC_URL
set -a; . ./.env; set +a
npm start
```

Откройте адрес, указанный в `API_PUBLIC_URL` (или `http://localhost:3000` для локальной разработки), и войдите с `ADMIN_PASSWORD`. При запуске без `.env` используются небезопасные значения для разработки (`change-me-now` и известный dev-secret) — не оставляйте их на сервере.

### Переменные окружения

| Переменная | Назначение |
| --- | --- |
| `PORT` | Порт HTTP-сервера, по умолчанию `3000` |
| `HOST` | Адрес привязки, по умолчанию `0.0.0.0` |
| `ADMIN_PASSWORD` | Пароль панели. Обязателен уникальный пароль в продакшене |
| `APP_SECRET` | Секрет HMAC для сессий и ссылок (не менее 32 случайных байт) |
| `API_PUBLIC_URL` | Публичный HTTPS origin сервиса, например `https://updates.example.com`, без завершающего `/` |
| `DATA_DIR` | Каталог базы JSON и приватных ZIP, по умолчанию `./data` |
| `NODE_ENV` | Поставьте `production`, чтобы включить флаг `Secure` у cookie панели |

Пример генерации секрета: `openssl rand -hex 32`. Smoke-тесты API запускаются командой `npm test`.

## Развёртывание

Сервис следует публиковать только за HTTPS reverse proxy (например, Nginx/Caddy). Проксируйте запросы на порт приложения и задайте `API_PUBLIC_URL` равным публичному HTTPS-адресу. Не публикуйте `DATA_DIR` через Nginx/Apache и не монтируйте его внутрь web-root. Сохраните каталог данных между перезапусками и регулярно делайте его резервную копию. Доступ к панели ограничьте надёжным паролем и, при необходимости, IP allowlist/VPN на reverse proxy.

Пример с Docker:

```bash
cp .env.example .env
# Заполните .env реальными секретами и публичным URL
docker compose up -d --build
```

Каталог `/var/lib/wp-panda` хранится в отдельном именованном Docker-томе `update-vault-data`. TLS в Compose не настраивается: используйте внешний reverse proxy и не открывайте порт приложения в интернет напрямую.

## Создание продукта и релиза

1. В панели нажмите **Добавить продукт**. Назначьте уникальные `slug` и тип (`plugin` или `theme`). Slug должен совпадать с именем директории установленного пакета.
2. Сохраните показанный API-ключ. Если он потерян, откройте **Подключение обновлений → Сменить ключ**; старый ключ сразу перестанет работать.
3. Загрузите ZIP с новой версией. В корне архива должна находиться папка с правильным slug, как в обычном ZIP для установки WordPress: `my-plugin/my-plugin.php` либо `my-theme/style.css`.
4. Введите версию, которая совпадает с версией в заголовках основного PHP-файла плагина или `style.css` темы. Приложение отдаёт наиболее новую версию.
5. Включите клиент обновлений в коде продукта (см. ниже). После обычной проверки WordPress Update API обновление появится в стандартной панели.

ZIP ограничен 100 МБ. Повторная загрузка того же номера версии заменяет архив этой версии.

## Подключение клиента WordPress

Скопируйте `wordpress/wp-panda-updater.php` в поставляемый пакет, например в корневую папку плагина, и подключите его из главного файла плагина. Укажите значения, созданные в панели:

```php
require_once __DIR__ . '/wp-panda-updater.php';

new WP_Panda_Updater(array(
    'type'       => 'plugin',
    'slug'       => 'my-private-plugin',
    'version'    => '1.0.0', // синхронизировать с Version: в заголовке плагина
    'api_url'    => 'https://updates.example.com',
    // 'plugin_file' => __FILE__, // можно задать явно, обычно определяется автоматически
));
```

Передайте ключ из `wp-config.php`, не из исходников распространяемого пакета:

```php
// wp-config.php
define('WP_PANDA_API_KEY', 'wpu_КЛЮЧ_ИЗ_ПАНЕЛИ');
```

По умолчанию SDK читает константу `WP_PANDA_API_KEY`. Ключ можно передать явно через `api_key`, либо указать отдельную константу для продукта через `'api_key_constant' => 'WP_PANDA_MY_PLUGIN_KEY'`.

Для темы подключите SDK из `functions.php` активной темы и передайте `type => 'theme'`, slug, текущую версию темы из `wp_get_theme()->get('Version')`, ключ и URL сервера:

```php
require_once get_stylesheet_directory() . '/wp-panda-updater.php';
$panda_theme = wp_get_theme();
new WP_Panda_Updater(array(
    'type'    => 'theme',
    'slug'    => $panda_theme->get_stylesheet(),
    'version' => $panda_theme->get('Version'),
    'api_key_constant' => 'WP_PANDA_API_KEY',
    'api_url' => 'https://updates.example.com',
));
```

Лучше не вшивать один и тот же секрет в публичные репозитории или общедоступный ZIP. Если ключ скомпрометирован, ротируйте его и распространите новый ключ в клиентской конфигурации. Для агентской дистрибуции разным клиентам нужна отдельная модель лицензий/ключей на установку — в этой версии используется общий ключ продукта.

SDK проверяет обновления с `sslverify=true`, регистрирует штатные WordPress-фильтры для плагинов/тем и получает временный URL архива. При недоступности сервера текущая версия сайта не блокируется. Для локального тестового HTTP-сервера можно определить `WP_PANDA_ALLOW_INSECURE_API`, но в продакшене используйте только HTTPS.

## API (для интеграции)

- `GET /api/v1/check?slug=...&type=plugin|theme&version=...` — заголовок `Authorization: Bearer <product-key>`. Возвращает `{"update":false}` или метаданные релиза с абсолютной временной `package`-ссылкой.
- `GET /download/:releaseId?expires=…&signature=…` — публичный маршрут, доступен только по корректной HMAC-подписи до истечения срока.
- `/api/admin/*` — панельные JSON-маршруты, закрыты подписанной HttpOnly/SameSite cookie.
- `GET /health` — проверка доступности сервиса.

Панель содержит один пароль администратора; для команды нескольких администраторов, лицензирования по доменам/сайтам, биллинга, аудита и RBAC потребуется расширить эту MVP-версию.

## Данные и безопасность

`data/catalog.json` содержит метаданные продуктов и хеши ключей. Архивы с рандомизированными именами лежат в `data/packages/`. Не коммитьте `data/`, не отдавайте его веб-сервером и не удаляйте при деплое. Подписанные ссылки действуют 10 минут и могут быть использованы повторно до истечения срока — обновляющий клиент WordPress должен скачать ZIP по HTTP. Протокол не мешает авторизованному получателю сохранить файл после законной загрузки: защита ограничивает прямое анонимное скачивание и раскрытие постоянного URL, но не DRM.
