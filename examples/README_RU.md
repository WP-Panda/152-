# Тестовые продукты WP Panda

В каталоге находятся два минимальных плагина и одна тема, подключённые к настоящему клиентскому SDK. Они нужны для ручной проверки выпуска релиза, отображения обновления без лицензии, отказа в скачивании без активации и успешной установки с лицензией. Пользовательских функций у продуктов почти нет.

## Состав и варианты экрана лицензии

| Slug в Vault | Тип | Проверяемый сценарий |
|---|---|---|
| `wp-panda-test-alpha` | Плагин | Автоматическая страница **Настройки → Panda Updates** |
| `wp-panda-test-beta` | Плагин | Собственная страница **Настройки → Panda Test Beta** с `wp_panda_updater_license_field()` |
| `wp-panda-test-theme` | Тема | Тема, подключающая SDK из `functions.php` |

Исходники находятся в `examples/fixtures/`. При сборке в каждый продукт автоматически включается актуальный `client/wp-panda-updater.php`; копию SDK вручную синхронизировать не нужно.

## 1. Настройте URL сервера на тестовом клиенте

До установки fixture добавьте в `wp-config.php` клиентского WordPress-сайта:

```php
define('WP_PANDA_VAULT_API_URL', 'https://updates.example.com/wp-json/wp-panda/v1');
```

Замените домен на адрес установленного WP Panda Vault. Это корень REST namespace; не добавляйте `/check` или `/download`. В исходниках есть демонстрационный fallback URL, который необходимо переопределить этой константой. Используйте HTTPS.

## 2. Соберите installable ZIP-файлы

Из корня репозитория выполните:

```bash
python3 examples/build-fixtures.py
```

Получатся:

```text
examples/build/wp-panda-test-alpha.zip
examples/build/wp-panda-test-beta.zip
examples/build/wp-panda-test-theme.zip
```

В ZIP находится верхний каталог со slug, основной PHP-файл/`style.css` и клиентский SDK. Эти ZIP предназначены и для установки на тестовый клиентский WordPress, и для загрузки в Panda Vault. Каталог `examples/build/` исключён из Git.

## 3. Создайте продукты и опубликуйте первую версию

На серверном WordPress в **Панель → Panda Vault** создайте три продукта с точными slug и типами из таблицы выше. Затем для каждого продукта:

1. Загрузите соответствующий ZIP из `examples/build/` как релиз версии **1.0.0**.
2. Выпустите отдельную тестовую лицензию с лимитом **1 сайт**. Ключи изолируйте от production и не публикуйте.
3. Сохраните выданный ключ для последующей активации на тестовом клиенте.

У каждого продукта свой slug, пакет и лицензия. Не загружайте ZIP Alpha в карточку Beta или темы.

## 4. Установите продукты на клиентский WordPress

На тестовом клиенте установите Alpha и Beta через **Плагины → Добавить новый → Загрузить плагин** из `examples/build/`, затем активируйте их. Для тестирования темы загрузите `wp-panda-test-theme.zip` через **Внешний вид → Темы → Добавить новую → Загрузить тему** и активируйте её.

Страницы ввода лицензии:

- Alpha и тема: **Настройки → Panda Updates**;
- Beta: **Настройки → Panda Test Beta**. Эта страница специально демонстрирует интеграцию блока лицензии в существующие настройки.

Для Beta сообщение о лицензии выводится через `wp_panda_updater_license_field()` внутри её собственного callback.

## 5. Проверьте доступ без ключа и с ключом

Чтобы увидеть обновление, не устанавливая его в базовый клиентский продукт:

1. На сервере соберите и загрузите релиз **1.0.1** для нужного тестового продукта.
2. В исходнике соответствующей fixture измените `Version:` в заголовке плагина либо `Version:` в `style.css` на `1.0.1`, затем снова выполните builder. Версия в header и форма загрузки релиза должны совпадать.
3. На клиенте без ключа нажмите **Консоль → Обновления → Проверить ещё раз**. WordPress должен показать новую версию.
4. Попробуйте установить её: сервер должен отказать в выдаче ZIP.
5. Активируйте выданный ключ на странице лицензии и повторите проверку/установку. Для активированного сайта скачивание должно пройти.
6. Отзовите лицензию или удалите активацию в Panda Vault и проверьте, что ранее выданная ссылка на пакет больше не работает.

Для тестирования отказа с невалидным ключом можно попытаться активировать случайное значение: оно не должно скрывать доступную версию, но активация и скачивание останутся недоступны.

## 6. Тестирование MU-loader’ов

Alpha и Beta являются активными плагинами и регистрируют SDK самостоятельно. Для отдельной проверки обновлений **неактивных** плагинов/тем установите соответствующий MU-loader из `client/loaders/` и добавьте служебный заголовок `Panda Vault Slug` согласно [руководству клиента](../client/README_RU.md). Не подключайте loader и собственный SDK одного продукта одновременно без необходимости.

## Важно

- Используйте тестовый Vault и тестовые лицензии, не клиентские production-ключи.
- Не публикуйте демонстрационный fallback `updates.example.com`; задавайте настоящий адрес через `WP_PANDA_VAULT_API_URL`.
- Эти fixture проверяют интеграцию и обновление, но не являются готовыми продуктами для продажи.
- Автоматическая CI-регрессия тестирует API-логику выдачи метаданных и блокировки пакета; полный тест всё равно проводите на staging с настоящим WordPress и InnoDB.
