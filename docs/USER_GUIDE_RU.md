# Полное описание и инструкция пользователя

## 1. Назначение системы

**WP Panda Update Vault** — собственный сервер распространения приватных ZIP-архивов WordPress-плагинов и тем. Он состоит из двух частей:

1. **Update Vault** — Node.js-приложение с веб-панелью, каталогом продуктов, закрытым файловым хранилищем и API обновлений.
2. **WP Panda Updater** — PHP-клиент `wordpress/wp-panda-updater.php`, который встраивается в код вашего плагина или темы.

Клиент подключает продукт к штатному процессу обновления WordPress. После публикации новой версии администратор сайта увидит обновление в **Консоль → Обновления** и в списке плагинов/тем. Архив устанавливает стандартный WordPress upgrader — отдельный механизм установки не создаётся.

### Поток обновления

1. WordPress запускает штатную проверку обновлений.
2. SDK отправляет серверу slug, тип продукта, установленную версию и ключ в HTTPS-запросе.
3. Vault сверяет ключ, ищет более новую опубликованную версию и возвращает метаданные.
4. Для архива формируется подписанный URL с ограниченным сроком действия (10 минут). В нём нет постоянного пути к ZIP или API-ключа.
5. WordPress скачивает ZIP и устанавливает его штатными средствами.

Архивы лежат в `DATA_DIR/packages`, а не в публичной папке сайта. Анонимный посетитель не может скачать ZIP по постоянной ссылке или открыть каталог файлов.

## 2. Что входит в текущую версию

- Панель с одним паролем администратора.
- Создание продуктов двух типов: `plugin` и `theme`.
- Загрузка ZIP до 100 МБ, версия и заметки к релизу.
- Выдача и ротация индивидуального ключа продукта; ключ показывается один раз.
- Проверка обновления и временная подписанная ссылка на архив.
- Отображение числа продуктов, релизов и скачиваний.
- Клиентский PHP SDK для обычных плагинов и тем.
- JSON-каталог и файловое хранение на диске.

Это MVP, не SaaS-платформа. Пока нет пользовательских ролей, учёта лицензий/доменов, оплаты, отдельных ключей на каждого клиента, автоматической почтовой доставки ключей и формы самообслуживания. У продукта один ключ API. Если выдавать его всем покупателям, любой получатель кода может прочитать его; ротация такого ключа отзовёт доступ у всех сайтов до распространения нового ключа. Механизм скрывает постоянный публичный URL и блокирует анонимное скачивание, но не является DRM и не защищает от уже авторизованного получателя.

## 3. Требования

### Сервер хранилища

- Node.js версии 18 или новее.
- Домен и TLS/HTTPS для публичного production-сервиса.
- Постоянное дисковое пространство для `DATA_DIR`.
- Reverse proxy (например, Nginx, Caddy или Traefik) либо иной способ завершения TLS.

### Сайты WordPress

- WordPress 5.8 или новее.
- PHP 7.4 или новее.
- Исходящие HTTPS-запросы с сайта к серверу обновлений.
- ZIP, который WordPress может установить как обычный архив плагина/темы.

## 4. Установка и локальный запуск

Из корня проекта:

```bash
cp .env.example .env
```

Сгенерируйте непредсказуемый секрет:

```bash
openssl rand -hex 32
```

Откройте `.env` и задайте реальные значения:

```dotenv
PORT=3000
HOST=0.0.0.0
NODE_ENV=production
ADMIN_PASSWORD=замените-на-уникальный-пароль-длиной-от-16-символов
APP_SECRET=вставьте-сюда-результат-openssl-rand-hex-32
API_PUBLIC_URL=https://updates.example.com
DATA_DIR=./data
```

Не используйте буквальные примеры из файла. В production приложение отказывается запускаться, если пароль/секрет оставлены шаблонными или URL не начинается с HTTPS.

Запуск в Linux/macOS/bash:

```bash
set -a
. ./.env
set +a
npm start
```

Локально откройте `http://localhost:3000`. Если `NODE_ENV=production`, браузерная сессия использует Secure-cookie, поэтому для теста через HTTP удобнее временно установить `NODE_ENV=development` и не выставлять сервер в Интернет.

Проверить доступность можно так:

```bash
curl http://localhost:3000/health
```

Ожидаемый результат: `{"ok":true}`.

### Запуск без `.env` в PowerShell

Для локального теста задайте переменные текущего процесса явно:

```powershell
$env:ADMIN_PASSWORD = "локальный-пароль"
$env:APP_SECRET = "длинный-локальный-секрет-не-менее-32-символов"
$env:API_PUBLIC_URL = "http://localhost:3000"
$env:NODE_ENV = "development"
node server.js
```

Не используйте HTTP и демонстрационные секреты в production.

## 5. Production-развёртывание

### Вариант A: Docker Compose

1. Настройте `.env` реальными секретами и публичным адресом `https://updates.example.com`.
2. Запустите:

   ```bash
   docker compose up -d --build
   ```

3. Контейнер слушает порт `3000` внутри Docker-сети. Compose не публикует этот порт наружу и сам не настраивает TLS.
4. Подключите к Docker-сети reverse proxy и направьте его на `update-vault:3000` (имя сервиса Compose).
5. Оставьте том `update-vault-data` постоянным: в нём находятся `catalog.json` и пакеты.
6. Проверьте HTTPS-адрес панели и endpoint `/health`.

Изменения кода приложения применяются после пересборки:

```bash
docker compose up -d --build
```

При обычном пересоздании контейнера именованный том сохраняется. Не выполняйте `docker compose down -v`, если не хотите безвозвратно удалить данные Vault.

### Вариант B: Node.js за Nginx

Запустите приложение локально на сервере и оставьте порт 3000 закрытым от внешнего Интернета. Пример базовой конфигурации Nginx (сертификаты TLS настраиваются отдельно):

```nginx
server {
    listen 443 ssl http2;
    server_name updates.example.com;

    # ZIP ограничен 100 MiB; оставьте запас на multipart-обвязку запроса.
    client_max_body_size 110m;

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 120s;
        proxy_request_buffering off;
    }
}
```

В `.env` обязательно задайте `API_PUBLIC_URL=https://updates.example.com`, `NODE_ENV=production`, сильный `ADMIN_PASSWORD` и случайный `APP_SECRET`. Приложение использует `API_PUBLIC_URL` для формирования абсолютных URL скачивания; оно не должно быть адресом localhost или внутренним именем контейнера.

Дополнительно рекомендуется:

- разрешить доступ к панели по VPN/IP allowlist;
- включить rate limit на вход и административные маршруты на reverse proxy;
- не публиковать папку `DATA_DIR` через Nginx/Apache и не хранить её в web-root;
- включить firewall, мониторинг диска и HTTPS с валидным сертификатом;
- не коммитить `.env` и `data/` в Git;
- ограничить права учётной записи, под которой работает приложение.

### Переменные окружения подробно

| Переменная | Значение и правила |
|---|---|
| `PORT` | TCP-порт; по умолчанию `3000`. За reverse proxy не обязательно публиковать его наружу. |
| `HOST` | Адрес прослушивания; обычно `0.0.0.0` в контейнере и `127.0.0.1` при локальном Nginx. |
| `ADMIN_PASSWORD` | Единственный пароль панели. В production — уникальная длинная строка минимум 16 символов. |
| `APP_SECRET` | Секрет HMAC для cookie сессии и ссылок скачивания; минимум 32 символа, предпочтительно 32 случайных байта или больше. Не меняйте без необходимости: действующие cookie и подписанные ссылки перестанут работать. |
| `API_PUBLIC_URL` | Публичный HTTPS origin, например `https://updates.example.com`, без завершающего `/` и без пути `/api`. |
| `DATA_DIR` | Каталог JSON-метаданных и приватных архивов. По умолчанию `./data`, в Docker — `/var/lib/wp-panda`. Должен находиться на постоянном диске. |
| `NODE_ENV` | Установите `production`: включается Secure-флаг cookie и проверяются обязательные production-настройки. |

### Обновление сервера и резервная копия

Перед обновлением кода приложения сохраните каталог данных. Для локальной установки достаточно остановить процесс и скопировать весь `DATA_DIR` целиком. Для Docker узнайте имя тома через `docker volume ls` и сделайте архив, например:

```bash
docker run --rm \
  -v ИМЯ_ТОМА:/data:ro \
  -v "$PWD":/backup \
  alpine tar -czf /backup/wp-panda-vault-backup.tar.gz -C /data .
```

В архиве должны быть `catalog.json` и каталог `packages/`. Проверяйте восстановление на отдельном экземпляре. Для согласованной резервной копии остановите приложение на время копирования.

## 6. Первый вход и создание продукта

1. Откройте публичный HTTPS URL сервиса.
2. Войдите с паролем `ADMIN_PASSWORD` из окружения.
3. Нажмите **Добавить продукт**.
4. Заполните:
   - **Название** — отображаемое имя, например `Panda SEO`;
   - **Slug** — идентификатор продукта из маленьких латинских букв, цифр, `_` или `-`, например `panda-seo`;
   - **Тип** — `Плагин` или `Тема`.
5. Проверьте, что slug точно совпадает с именем каталога продукта внутри ZIP. Регистр и дефисы важны.
6. Сохраните выданный ключ. Он показывается только один раз. При потере можно выпустить новый из раздела подключения, но старый ключ сразу перестанет работать.

В панели ключ — доступ к проверке обновлений для данного продукта. Не отправляйте его в публичные тикеты и не помещайте в общедоступный репозиторий.

## 7. Как собрать правильный ZIP

### Плагин

Пример структуры проекта:

```text
panda-seo/
├── panda-seo.php
├── includes/
└── assets/
```

В заголовке главного PHP-файла должна стоять та же версия, которую вы выпустите:

```php
/*
Plugin Name: Panda SEO
Version: 1.2.0
*/
```

Архив должен содержать каталог верхнего уровня `panda-seo/`, а не только файлы плагина. Создайте ZIP из родительского каталога:

```bash
zip -r panda-seo-1.2.0.zip panda-seo/
unzip -l panda-seo-1.2.0.zip | head
```

### Тема

```text
panda-theme/
├── style.css
├── functions.php
├── index.php
└── wp-panda-updater.php
```

В `style.css` задайте корректные заголовки:

```css
/*
Theme Name: Panda Theme
Version: 1.2.0
*/
```

ZIP также должен содержать папку `panda-theme/` в корне.

### Публикация релиза

1. Откройте продукт в каталоге.
2. Нажмите **Загрузить релиз**.
3. Укажите числовую версию, например `1.2.0` или `2.0`; система принимает до четырёх числовых частей.
4. Выберите ZIP размером до 100 МБ.
5. Добавьте необязательное описание изменений.
6. Нажмите **Опубликовать релиз**.

Версия в панели должна совпадать с версией в коде. Наиболее высокая числовая версия считается текущей и предлагается сайтам. Релиз с версией, уже присутствующей у продукта, заменяет прежний ZIP этой версии. Чтобы повторно выдать исправленный архив, загружайте его под тем же номером только если понимаете, что WordPress может считать версию уже установленной; для обычного исправления безопаснее повысить версию.

## 8. Встраивание SDK в плагин

Скопируйте `wordpress/wp-panda-updater.php` в каталог плагина, например рядом с главным PHP-файлом. Добавьте регистрацию в основной файл:

```php
<?php
/*
Plugin Name: Panda SEO
Version: 1.0.0
*/

if (!defined('ABSPATH')) {
    exit;
}

require_once __DIR__ . '/wp-panda-updater.php';

new WP_Panda_Updater(array(
    'type'    => 'plugin',
    'slug'    => 'panda-seo',
    'version' => '1.0.0',
    'api_url' => 'https://updates.example.com',
    // 'plugin_file' => __FILE__, // при необходимости задайте путь плагина явно
));
```

Ключ рекомендуется хранить в `wp-config.php` сайта WordPress, а не в публичном исходнике:

```php
// Добавьте выше строки "That's all, stop editing!"
define('WP_PANDA_API_KEY', 'wpu_КЛЮЧ_ИЗ_ПАНЕЛИ');
```

По умолчанию SDK читает эту константу. Можно передать `api_key` прямо в конфигурации (небезопасно для публичного пакета) или использовать `api_key_constant`, если для разных продуктов заданы отдельные имена констант:

```php
new WP_Panda_Updater(array(
    'type' => 'plugin',
    'slug' => 'panda-seo',
    'version' => '1.0.0',
    'api_key_constant' => 'WP_PANDA_PANDA_SEO_KEY',
    'api_url' => 'https://updates.example.com',
));
```

И в `wp-config.php`:

```php
define('WP_PANDA_PANDA_SEO_KEY', 'wpu_КЛЮЧ_ИЗ_ПАНЕЛИ');
```

Если основной файл плагина лежит не там, где SDK может его автоматически обнаружить, явно укажите `'plugin_file' => __FILE__` из главного файла плагина.

## 9. Встраивание SDK в тему

Положите `wp-panda-updater.php` в корень темы. В `functions.php` добавьте:

```php
<?php
require_once get_stylesheet_directory() . '/wp-panda-updater.php';

$panda_theme = wp_get_theme();
new WP_Panda_Updater(array(
    'type' => 'theme',
    'slug' => $panda_theme->get_stylesheet(),
    'version' => $panda_theme->get('Version'),
    'api_key_constant' => 'WP_PANDA_API_KEY',
    'api_url' => 'https://updates.example.com',
));
```

Slug темы WordPress — имя её каталога (для активной дочерней темы это stylesheet slug). Это значение должно совпасть со slug продукта в панели и с верхним каталогом ZIP. Версия читается из `Version:` в `style.css`.

## 10. Проверка обновления на WordPress-сайте

1. Установите первую сборку плагина/темы любым стандартным способом.
2. Добавьте SDK и конфигурацию до сборки ZIP, который загружаете в Vault.
3. Добавьте нужный ключ в `wp-config.php` на тестовом WordPress-сайте.
4. Убедитесь, что сайт открывает `https://updates.example.com` и исходящие HTTPS-запросы не заблокированы.
5. Опубликуйте релиз с версией выше установленной.
6. В панели WordPress откройте **Консоль → Обновления → Проверить ещё раз**.
7. Установите обновление стандартной кнопкой WordPress.
8. Убедитесь, что версия продукта изменилась, а счётчик скачиваний в Vault увеличился.

Если тестируется обновление уже установленного пакета, измените версию и в основном файле плагина/`style.css`, и в SDK-конфигурации, затем упакуйте новую сборку. Для темы при использовании `$panda_theme->get('Version')` значение берётся из заголовка темы.

## 11. Ротация ключа, удаление и секреты

### Ротация

Откройте продукт → **Документация интеграции** → **Сменить ключ**. Подтвердите действие и сохраните новый ключ. Старый ключ немедленно перестанет проходить проверку. Обновите константу на всех обслуживаемых WordPress-сайтах. До этого сайты не смогут проверять обновления.

### Удаление

Удаление продукта удаляет записи релизов и соответствующие ZIP-архивы. Операция необратима. Перед удалением сделайте резервную копию, если архивы нужны.

### Что защищено, а что нет

- Нельзя анонимно перечислить или скачать архивы по постоянному пути.
- Время действия подписанного URL ограничено десятью минутами; путь к файлу рандомизирован.
- Временную ссылку можно использовать повторно до окончания срока.
- Установленный пакет после скачивания доступен администратору сайта; запретить его копирование нельзя.
- Если общий API-ключ вшит в публичный ZIP или опубликован в клиентском коде, его можно извлечь. Храните его вне публичного пакета и выдавайте только доверенным сайтам. Для коммерческой дистрибуции по клиентам необходимы индивидуальные лицензии/ключи и серверная проверка лицензии — в данной версии это не реализовано.
- Используйте только HTTPS. SDK не отправляет ключ на HTTP, кроме локального режима при явном включении `WP_PANDA_ALLOW_INSECURE_API`.

## 12. API и проверка сервиса

### Проверка обновления

```bash
curl -i \
  -H 'Authorization: Bearer wpu_ВАШ_КЛЮЧ' \
  'https://updates.example.com/api/v1/check?slug=panda-seo&type=plugin&version=1.0.0'
```

При отсутствии релиза или установленной актуальной версии ответ будет:

```json
{"update":false}
```

При доступном обновлении сервер возвращает `version`, `changelog`, `type`, `slug` и `package` — временную подписанную ссылку. Проверяйте `/health` мониторингом:

```bash
curl -fsS https://updates.example.com/health
```

### Основные маршруты

| Маршрут | Назначение |
|---|---|
| `GET /health` | Проверка доступности приложения. |
| `GET /api/v1/check?slug=…&type=plugin\|theme&version=…` | Проверка релиза с `Authorization: Bearer <key>`. |
| `GET /download/:releaseId?expires=…&signature=…` | Временная подписанная загрузка ZIP. |
| `/api/admin/*` | Панельные маршруты с авторизацией cookie; используйте веб-интерфейс. |

## 13. Устранение неполадок

### Продукт не появляется в обновлениях WordPress

Проверьте по порядку:

1. В Vault опубликована версия строго выше текущей версии продукта.
2. Slug совпадает в панели, каталоге ZIP и конфигурации SDK. Для плагина `slug` обычно соответствует папке плагина; для темы — stylesheet slug.
3. Для плагина SDK подключён из главного файла и при необходимости правильно задан `plugin_file`.
4. Ключ в `wp-config.php` соответствует именно этому продукту и не был ротирован.
5. В `api_url` указан публичный HTTPS origin без `/api` в конце.
6. Сервер WordPress может выполнять исходящие HTTPS-запросы; PHP cURL/OpenSSL и сертификаты актуальны.
7. В WordPress нажата кнопка **Проверить ещё раз**. SDK кэширует результат проверки максимум на пять минут; кеш обновлений WordPress также может влиять на отображение.

### Ошибка 401 при проверке

Ключ неверный, продукт/тип/slug не совпали либо ключ был отозван ротацией. Сохраните новый ключ в `wp-config.php`. Не передавайте ключ как URL-параметр: сервер ожидает `Authorization: Bearer`.

### Ошибка скачивания или истёкшая ссылка

Проверьте, что `API_PUBLIC_URL` содержит внешний HTTPS-домен, доступный с WordPress-сервера. Не задавайте `localhost`, IP внутренней сети или URL, недоступный извне. Ссылка действительна 10 минут; клиент запрашивает новую, если выполняет новую проверку. Убедитесь, что reverse proxy проксирует `/download/…` к приложению.

### ZIP не загружается в панель

- Убедитесь, что файл — ZIP и начинается с корректного ZIP-содержимого.
- Максимальный размер — 100 МБ; на Nginx поднимите `client_max_body_size` минимум до `110m`.
- Проверьте свободное место и права на `DATA_DIR`.
- Проверьте, что внутри ZIP есть каталог продукта верхнего уровня.

### WordPress не может установить архив

Скачайте ZIP временной ссылкой для диагностики и проверьте его структуру. Архив должен иметь вид `slug/главный-файл`, а не `папка-сборки/slug/главный-файл` и не набор файлов без каталога продукта. Проверьте, что архив не повреждён и сервер не изменяет ZIP при проксировании.

### Панель не принимает пароль / сессия не сохраняется

Проверьте `ADMIN_PASSWORD`, домен и cookie браузера. При `NODE_ENV=production` cookie помечена Secure и браузер отправляет её только по HTTPS; за reverse proxy используйте внешний HTTPS URL. Если менялся `APP_SECRET`, войдите заново — прежние сессии становятся недействительными.

### Production-приложение не запускается

Посмотрите лог процесса. Проверьте обязательные значения: `ADMIN_PASSWORD` минимум 16 символов, `APP_SECRET` минимум 32 символа, `API_PUBLIC_URL` начинается с `https://`. Шаблонные значения `.env.example` нужно заменить.

## 14. Частые вопросы

**Нужно ли устанавливать отдельный плагин из WordPress.org?** Нет. SDK включается в исходный код вашего плагина или темы.

**Кто скачивает ZIP?** Сам WordPress-сайт через стандартный upgrader после того, как SDK зарегистрировал доступное обновление.

**Можно ли размещать Vault на том же сервере, что и WordPress?** Да, но `DATA_DIR` должен оставаться закрытым от веб-сервера, а API — доступным по HTTPS.

**Можно ли выпускать beta-версии?** Сейчас версия релиза должна состоять из числовых частей (`1.2`, `1.2.3` и т.п.); prerelease-суффиксы вроде `1.2.0-beta` этой версией не поддерживаются.

**Можно ли задавать WordPress-совместимость и PHP-версию для каждого релиза в панели?** Пока нет: API использует текущие значения по умолчанию в `server.js`. Для такой функции следует добавить поля совместимости в форму и метаданные релиза.

**Это защищает от копирования после установки?** Нет. Это контролируемая раздача обновлений, а не DRM. Авторизованный сайт должен получить ZIP, и его администратор имеет доступ к файлам.
