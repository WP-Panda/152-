# WP Panda Vault — руководство по серверу издателя

Это подробное руководство описывает серверную сторону WP Panda Vault: установку, хранение приватных ZIP, настройку API, создание продуктов и выпуск лицензий, эксплуатацию и резервное копирование. Все административные операции выполняются в WordPress; отдельный Node.js-сервис или SaaS-панель не требуются.

## 1. Состав системы и путь обновления

`server/wp-panda-vault/` — обычный WordPress-плагин, который устанавливается на сайте издателя. Он добавляет меню **Панель → Panda Vault**, создаёт таблицы в базе WordPress, публикует REST API и хранит пакеты в отдельном закрытом каталоге.

Полный цикл:

1. Издатель создаёт продукт типа `plugin` или `theme` и загружает ZIP-релиз.
2. Vault проверяет структуру ZIP и версию, копирует архив в закрытое хранилище и сохраняет его SHA-256.
3. Издатель создаёт отдельный лицензионный ключ на 1, 3 или 5 сайтов. Сырой ключ показывается один раз.
4. Клиент встраивает SDK из `client/`, а администратор клиентского сайта активирует ключ. Vault регистрирует canonical host/path сайта.
5. При стандартной проверке клиент получает публичные метаданные релиза, поэтому WordPress может показать новую версию даже без ключа или с невалидным ключом. Только действующая лицензия с активацией этого сайта получает ссылку, которая разрешает скачивание.
6. При каждом скачивании сервер повторно проверяет срок и HMAC-подпись, текущий статус лицензии и активацию сайта, нахождение файла в приватном каталоге и SHA-256 содержимого.

Путь запроса и примеры клиентского кода подробно описаны в [руководстве клиента](../client/README_RU.md).

## 2. Требования и подготовка сервера

- WordPress **6.0+**, PHP **7.4+**.
- Расширение PHP `ZipArchive` для проверки ZIP при публикации релиза.
- Записываемый PHP-процессом локальный каталог **за пределами `ABSPATH` и web-root**.
- HTTPS с действительным TLS-сертификатом для публичного сервера; исходящие подключения клиентов должны доверять этому сертификату.
- Достаточные лимиты PHP, веб-сервера и прокси на приём ZIP. Лимит Vault по умолчанию — 200 MiB.
- Регулярная резервная копия базы и каталога закрытого хранилища.

Рекомендуется отдельный актуальный WordPress-инстанс издателя с ограниченным числом администраторов, MFA и мониторингом диска. REST-маршруты лицензирования открыты для HTTP-запросов, поскольку клиентская аутентификация осуществляется уникальными ключами; HTTPS обязателен для их защиты при передаче.

## 3. Установка и конфигурация приватного каталога

1. Скопируйте каталог `server/wp-panda-vault/` в `wp-content/plugins/wp-panda-vault/` на серверном WordPress либо соберите ZIP так, чтобы главным каталогом архива был `wp-panda-vault/`.
2. До активации выберите закрытый каталог. По умолчанию Vault создаёт `wp-panda-vault-private` рядом с `ABSPATH`; фактический путь проверяется и должен быть вне `ABSPATH` и `DOCUMENT_ROOT`.
3. Если путь по умолчанию недоступен, задайте в `wp-config.php` до строки завершения редактирования:

   ```php
   define('WP_PANDA_VAULT_STORAGE_DIR', '/var/lib/wp-panda-vault/site-1');
   define('WP_PANDA_VAULT_SECRET', 'ВСТАВЬТЕ_СЛУЧАЙНЫЙ_СЕКРЕТ_МИНИМУМ_32_СИМВОЛА');
   ```

   Секрет можно создать, например, `openssl rand -hex 32`. Если `WP_PANDA_VAULT_SECRET` не задан, подпись использует WordPress AUTH salt. Явный секрет полезен, когда соли меняются независимо или нужно управляемо сохранять секрет при миграции.
4. Для заданного вручную каталога создайте отдельную директорию с владельцем PHP-процесса и правами `0700` (например, `install -d -m 0700 -o www-data -g www-data /var/lib/wp-panda-vault/site-1`, заменив пользователя/группу на свои). Vault не меняет права уже существующих каталогов и откажется использовать каталог с более широкими правами на Unix-системах. Автоматически созданный конечный каталог получает `0700`, ZIP — `0600` (если файловая система поддерживает Unix-права).
5. Не задавайте системный каталог или его родителя (`/var`, `/home`, `/tmp`, `/usr`, `/etc` и т. п.) как хранилище; используйте отдельную директорию. Активируйте **WP Panda Vault** и убедитесь, что в **Панель → Panda Vault** нет предупреждения о хранилище.

Не используйте `wp-content/uploads`, публичный web-root, общую временную папку или Git для хранения ZIP. Убедитесь, что backup- и deployment-процессы не открывают хранилище для web-сервера.

### Лимиты загрузки

PHP и reverse proxy должны разрешать загрузку, превышающую максимальный пакет. Пример Nginx:

```nginx
client_max_body_size 210m;
```

В PHP настройте `upload_max_filesize` не меньше ожидаемого ZIP и `post_max_size` немного выше. По умолчанию собственный лимит Vault составляет 200 MiB; его можно изменить в `wp-config.php` (байты):

```php
define('WP_PANDA_VAULT_MAX_PACKAGE_SIZE', 300 * 1024 * 1024);
```

Это не обходит меньшие ограничения PHP/proxy. `ZipArchive` должен быть доступен именно в том PHP SAPI, который обслуживает WordPress.

## 4. База данных и жизненный цикл

При запуске плагин управляет таблицами с текущим префиксом `$wpdb->prefix`:

- `*_panda_vault_products` — slug, тип и название продуктов;
- `*_panda_vault_releases` — версии, changelog, путь/размер/SHA-256 пакета и требования;
- `*_panda_vault_licenses` — SHA-256 ключа, метка, лимит и статус;
- `*_panda_vault_activations` — URL площадок и отметки активации/последней проверки.

Схема обновляется через механизм WordPress `dbDelta`. При обычной деактивации плагина данные не удаляются. Удаление продукта из интерфейса — разрушительная операция: она удаляет его лицензии, активации, релизы и связанные файлы в приватном хранилище. Перед удалением сделайте backup, если данные нужны для аудита.

Для атомарного контроля лимитов активаций таблицы должны работать на **InnoDB**; миграция схемы пытается привести их к этому движку и не отмечает версию схемы обновлённой при ошибке. Убедитесь, что учётная запись БД имеет необходимые права на `ALTER TABLE`. На multisite таблицы и администрирование относятся к тому сайту, на котором установлен/включён плагин; планируйте контекст установки и префикс базы заранее.

## 5. Создание продукта

1. В меню **Панель → Panda Vault** найдите форму **Добавить продукт**.
2. Укажите человекочитаемое название.
3. Выберите уникальный slug длиной 2–60 символов: строчные латинские буквы, цифры, `_` или `-`, первый символ — буква или цифра (например `panda-seo`). Slug должен совпадать с каталогом в ZIP и конфигурацией SDK.
4. Выберите тип: `plugin` или `theme`. Одинаковые slug могут использоваться у разных типов, но для понятности используйте соответствующий slug расширения/темы.
5. Создайте продукт. Откройте его страницу, нажав по названию в каталоге.

Изменение slug после выпуска продукта требует синхронно обновить SDK/заголовки, так как slug — часть идентичности продукта и лицензии.

## 6. Сборка и публикация ZIP-релиза

### Формат архива плагина

ZIP должен содержать один корневой каталог, равный slug, главный PHP-файл с WordPress Plugin Header и корректной версией. Например:

```text
panda-seo.zip
└── panda-seo/
    ├── panda-seo.php
    ├── wp-panda-updater.php
    └── includes/...
```

Версия в `Version:` главного PHP-файла должна точно совпадать с версией, введённой при загрузке. В основной файл включите SDK (пример — в [руководстве клиента](../client/README_RU.md)).

### Формат архива темы

ZIP должен иметь один верхний каталог со slug темы. В корневом `style.css` должны находиться заголовки `Theme Name:` и `Version:`; версия должна совпасть с указанной в форме релиза. Заголовок темы, который WordPress использует для обновления, и slug должны оставаться согласованными.

### Загрузка

1. В карточке продукта используйте форму добавления релиза.
2. Укажите версию в числовом формате `1`, `1.2`, `1.2.3` или `1.2.3.4`.
3. Выберите ZIP и заполните changelog, минимальные требования WordPress/PHP и проверенную версию WordPress (если известна).
4. Отправьте форму и устраните показанную проверочную ошибку, если пакет не прошёл валидацию.

Проверки включают ZIP-сигнатуру и читаемость, допустимый размер архива, число записей (до 20 000), суммарный распакованный размер (до 1 GiB), размер отдельной записи (до 256 MiB), предельный коэффициент сжатия для крупных записей, единственный верхний каталог со slug, отсутствие traversal-путей и symlink-записей, наличие главного файла и согласованность версии. Публикация той же версии заменяет прежний пакет этой версии; перед повторной загрузкой проверьте точность содержимого. Номер версии, который ниже или равен установленному, не будет предложен SDK как обновление.

После успешной загрузки Vault сохраняет архив под случайным именем, внепублично, вычисляет SHA-256 и хранит метаданные релиза. Прямой постоянной ссылки на архив нет.

## 7. Выпуск индивидуальных лицензий

1. На карточке продукта найдите раздел **Лицензии и активации сайтов**.
2. Введите необязательную метку: заказ, организацию или имя клиента. Не записывайте секретные данные клиента в метку.
3. Выберите лимит **1**, **3** или **5**.
4. Нажмите **Выпустить лицензию**.
5. Скопируйте ключ из одноразового уведомления и безопасно передайте клиенту. Ключ повторно не показывается; если он потерян, отзовите его и выпустите новый.

Ключ генерируется криптографически стойким генератором. Vault нормализует его и сохраняет только SHA-256-хеш; исходного значения в базе нет. Поэтому backup базы не позволяет восстановить ключ, который клиент потерял. Клиент хранит ключ в опции WordPress без autoload; ключ нельзя добавлять в общий ZIP, Git, документацию или публичные логи.

У каждой лицензии свой лимит и список активаций. Состояние `revoked` блокирует проверки обновлений и новые активации. В текущей версии отсутствуют сроки действия лицензий, платежи/подписки, автоматическая выдача/письма покупателям и личный кабинет клиента — выпуск, передача и отзыв ключей выполняются администратором вручную.

## 8. Активации и администрирование слотов

На странице продукта разверните/просмотрите строку лицензии. Vault показывает статус, число `активации / лимит`, URL, время активации и последней проверки.

- **Освободить слот** удаляет одну запись площадки; ключ остаётся активен и его можно активировать снова.
- **Отозвать** блокирует ключ для всех сайтов. Используйте при утечке/окончании права доступа; отзыв не эквивалентен освобождению одного слота.
- Если сайт удалён, переехал, потерял ключ или больше не отвечает, администратор может освободить запись в Vault.
- Клиентская деактивация обращается к API, чтобы удалить именно текущую площадку.

Идентификатор площадки формируется из нормализованных host, нестандартного порта и пути WordPress. Схема HTTP/HTTPS исключена из идентификатора, поэтому переезд того же host/path с HTTP на HTTPS сохраняет один слот. Стандартные порты 80/443 нормализуются; завершающие/повторные `/` пути приводятся к одной форме. Поддомены и разные подкаталоги считаются разными площадками. Повторная активация того же identity идемпотентна.

Это контроль использования, а не доказательство владения доменом: API принимает переданный клиентом `site_url`, DNS/HTTP challenge не выполняется. Злоумышленник с полученным ключом может попытаться сообщить другой URL; не трактуйте механизм как DRM.

## 9. REST API и URL сервера

По умолчанию корень API имеет вид:

```text
https://updates.example.com/wp-json/wp-panda/v1
```

Фактический host — домен WordPress-издателя. Для клиента передавайте корень namespace, **без** `/check`, `/license/...` и `/download/...`. При нестандартном REST prefix или конфигурации permalink проверяйте REST URL на сайте издателя и в сгенерированном коде на странице продукта.

### Проверка обновления

```http
GET /check?slug=panda-seo&type=plugin&version=1.2.0&site_url=https%3A%2F%2Fshop.example.com%2F
Authorization: Bearer WPPV-<license-key>   # заголовок необязателен
Accept: application/json
```

Без более новой версии ответ содержит `{"update":false}`. При наличии релиза сервер возвращает версию, changelog, требования и поле `package` даже без ключа или с неверным ключом — это необходимо WordPress, чтобы показать сам факт обновления. В этом случае `package` указывает на закрытый маршрут и скачивание завершится HTTP 403. Только если Bearer-ключ действителен и сайт активирован, сервер выдаёт подписанный URL; при скачивании лицензия и активация проверяются повторно. Поэтому считайте version/changelog публичными метаданными и не помещайте туда закрытую информацию.

### Активация и деактивация

`POST /license/activate` и `POST /license/deactivate` принимают JSON:

```json
{
  "slug": "panda-seo",
  "type": "plugin",
  "license_key": "WPPV-...",
  "site_url": "https://shop.example.com/"
}
```

Успешная активация сообщает `activations` и `limit`. При исчерпании слотов ответ имеет HTTP 409; неверный/отозванный ключ обычно даёт HTTP 403. Деактивация удаляет активацию URL, но допускается и для отозванной лицензии, чтобы освободить слот.

### Скачивание пакета

`GET /download/{id}` без параметров возвращает отказ в скачивании: такой URL нужен WordPress для отображения обновления в интерфейсе, но он не даёт получить ZIP. Авторизованный клиент получает URL `GET /download/{id}?expires=...&license_id=...&site_hash=...&signature=...`. Подпись HMAC-SHA256 действует 48 часов — это покрывает обычный срок кэширования update transient в WordPress. Она привязана к релизу, ID лицензии, хешу площадки и сроку; URL не содержит исходный ключ. При фактическом скачивании сервер повторно проверяет подпись, активный статус лицензии, наличие активации именно этой площадки, закрытый путь и SHA-256 пакета. Отзыв лицензии или удаление активации блокируют ранее выданную ссылку.

## 10. Безопасность и конфиденциальность

- Метаданные релизов доступны без ключа, чтобы показывать обновления; скачивание пакетов требует краткоживущий подписанный URL и повторную проверку действующей лицензии/активации. Применяйте TLS везде.
- Админские формы проверяют `manage_options` и nonce.
- Ключи лицензий хранятся в Vault как SHA-256-хеши, исходный ключ показывается один раз.
- ZIP размещён вне `ABSPATH`/web-root, получает непредсказуемое имя и проверяется по checksum перед выдачей.
- Установите лимиты размера, защиту от brute force на уровне инфраструктуры при необходимости и мониторьте частые неуспешные запросы.
- Ограничьте `manage_options`, применяйте MFA и обновляйте WordPress/PHP.
- Не отправляйте ключи в тикеты/логи; если ключ раскрыт, отзовите его и выдайте новый.
- Не размещайте хранилище или ключи в общедоступном backup-репозитории.

Подписанный URL — bearer-ссылка: его обладатель может повторять скачивание до истечения 48 часов, пока лицензия и привязка активации остаются действующими. Отзыв лицензии и удаление активации прекращают доступ сразу, но утечка ссылки всё равно допускает скачивание в течение оставшегося срока. Не помещайте URL в публичные логи/тикеты, используйте TLS и ограничивайте доступ к журналам. Поскольку скачанный клиентом ZIP нельзя контролировать после установки, Vault не препятствует копированию уже легально полученного файла.

## 11. Резервное копирование, восстановление и миграция

Согласованно резервируйте:

1. Четыре таблицы `*_panda_vault_products`, `*_panda_vault_releases`, `*_panda_vault_licenses`, `*_panda_vault_activations`.
2. Весь каталог `WP_PANDA_VAULT_STORAGE_DIR` (или фактический каталог по умолчанию).
3. `wp-config.php`, включая `WP_PANDA_VAULT_SECRET`, если он задан.

Путь к ZIP хранится в базе. Восстанавливайте БД и каталоги как одну точку времени; после миграции проверьте, что все `package_path` указывают на существующие файлы внутри нового закрытого каталога, PHP может читать/записывать его, а веб-сервер не отдаёт его напрямую. Если абсолютный путь изменился, перенесите файлы в ожидаемое место либо контролируемо обновите пути в release-таблице и перепроверьте целостность.

Сохраняйте signing secret при миграции, если хотите, чтобы ранее выданные ссылки продолжали проходить проверку до истечения. Изменение AUTH salts/секрета аннулирует прежние download signatures, что безопасно; клиент запросит новую ссылку при следующей проверке.

## 12. Эксплуатация и диагностика

### Меню Vault не отображается

Убедитесь, что активен плагин на нужном WordPress-сайте и текущая учётная запись имеет `manage_options`. В multisite проверьте, что плагин установлен и включён в том контексте сайта, где требуется каталог.

### Ошибка приватного хранилища

Проверьте абсолютный путь, существование/права родительского каталога, владельца PHP-процесса и свободное место. Путь не должен разрешаться внутрь `ABSPATH` или `DOCUMENT_ROOT`. Задайте `WP_PANDA_VAULT_STORAGE_DIR` в `wp-config.php`, создайте каталог заранее, назначьте права PHP-пользователю и повторите проверку.

### Загрузка ZIP не проходит

Проверьте наличие `ZipArchive`, `upload_max_filesize`, `post_max_size`, Nginx `client_max_body_size`, лимит `WP_PANDA_VAULT_MAX_PACKAGE_SIZE` и свободное место. Убедитесь, что архив — валидный ZIP, его корневая папка совпадает со slug, содержит главный файл с версией, соответствующей форме. Не упаковывайте дополнительную вложенную папку вроде `release/panda-seo/...`.

### Скачивание ZIP получает 403 / активация получает 403 или 409

- HTTP 403 на `/download/{id}` без подписанных параметров — ожидаемое поведение для сайта без действующей активированной лицензии; версия при этом должна оставаться видна в WordPress.
- HTTP 403 при активации — неверный/отозванный ключ или неправильный продукт; при проверке entitlement проверьте, что сайт активирован именно на этой лицензии.
- HTTP 409 при активации — лимит слотов исчерпан; проверьте список площадок и освободите устаревший слот.
- Убедитесь, что клиент передаёт canonical `home_url('/')`, а URL сервера задан как корень API namespace.

### Обновление не отображается, хотя релиз загружен

Увеличьте номер версии релиза; Vault не предлагает версию, которая не новее установленной. Проверьте slug/type, опубликованный пакет и доступность REST endpoint. Наличие ключа не должно влиять на отображение новой версии. Учитывайте клиентский кэш до пяти минут и кэш transients WordPress; инициируйте повторную проверку после очистки релевантного кэша.

### Подписанная загрузка возвращает 403 или 404

Подписанная ссылка действует 48 часов; по истечении срока клиенту нужно повторно проверить обновления. При этом отзыв лицензии или удаление активации блокируют URL немедленно. При проблеме на стороне хранилища проверьте файл и SHA-256; при переносе — абсолютный путь и `WP_PANDA_VAULT_STORAGE_DIR`. Смена секрета делает ранее созданные ссылки недействительными.

## 13. Перед запуском в production

GitHub Actions проверяет синтаксис PHP в диапазоне 7.4–8.3, запускает изолированные регрессионные проверки видимости обновления/защиты скачивания (`php tests/update-visibility.php`) и собирает три installable test fixtures через `python3 examples/build-fixtures.py`. Это не заменяет тест на настоящем WordPress, MySQL/InnoDB, PHP ZipArchive и реальном WordPress Upgrader — эти интеграционные проверки нужно пройти отдельно на staging.

- Проверьте создание продукта, валидный и невалидный ZIP, версию/changelog и повторную публикацию версии.
- На тестовых клиентах проверьте лимиты 1/3/5, дублирующую активацию одного сайта, превышение лимита, деактивацию, освобождение слота, отзыв и получение обновления.
- Проверьте перенос между HTTP/HTTPS и различие host/path согласно ожидаемой политике подсчёта.
- Убедитесь, что архив недоступен напрямую по web URL и доступен только через подписанный download endpoint.
- Выполните тест восстановления базы и хранилища из backup.
- Зафиксируйте процедуру безопасной передачи ключей, отзыва и ручного освобождения слотов.

Интеграция клиента описана отдельно: **[client/README_RU.md](../client/README_RU.md)**.
